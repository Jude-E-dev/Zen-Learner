## Problem Statement

Grinding math practice problems is boring, and generic AI tutoring (ChatGPT, Gemini, Claude, Khanmigo) already solves "explain this to me" for free — but none of it makes the *practice loop itself* engaging or builds durable retention. The goal is a self-contained vertical slice — pick a topic, enter a game-like grind of authored practice questions, earn XP, climb mastery-gated ranks, and when stuck, pause into a tightly constrained tutor before resuming — built primarily to solve the builder's own need to practice/relearn first-year calculus. (Linear algebra was in the original scope and is deferred; see NOT in scope.)

## What Makes This Cool

A 16-bit ronin aesthetic wrapped around real math grinding: chunky pixel-font damage numbers on correct answers, keyboard-only input (Enter submits, Enter advances — a run of 20-30 questions without touching the mouse), a rank-up moment built to be visually loud, and a post-session summary card deliberately composed to be screenshot-worthy. The twist is the tutor pause: get stuck, the world visibly quiets, a hint-ladder tutor helps with the *specific mistake just made* — never solves it outright — then drops the learner back into the grind mid-stream with the question intact.

## Constraints

1. **The question bank is the product.** Authored, versioned, schema-validated content files under `content/`. Never LLM-generated at runtime, never stored only in a database.

   **Answer equivalence (revised — eng review issues 3, and tension 1).** Answers are checked by *behavior*, not spelling: parse both the learner's input and the answer key with `mathjs`, then evaluate both at several sample points and accept if all agree within tolerance. This replaces the original per-question enumerated alternate-form lists, which carried an unbounded authoring cost and would still miss forms nobody thought to enumerate. Three edge cases are load-bearing and must be built, not discovered:
   - **Antiderivatives.** Two correct answers to an indefinite integral differ by an arbitrary constant and will never agree pointwise. Either differentiate both before comparing, or compare `F(b) - F(a)` across sample pairs so the constant cancels. Without this, every correct integral is marked wrong — and integration by parts and u-substitution are core content.
   - **Domain safety.** Trig, log, and sqrt answers have restricted domains, branch cuts, and removable discontinuities. Reject any sample point where either expression is undefined and resample from a safe domain.
   - **Failure means unreadable, never wrong.** If sampling can't be completed after resampling, treat the input as unparseable (see #11), never as an incorrect answer. A false "wrong" on a correct answer is the fastest way to destroy trust in a practice tool.

   String normalization (case-insensitive, whitespace-collapsed, LaTeX delimiters stripped) still runs first as a fast path. Per-question declared alternate forms survive only as an escape hatch for answers that aren't numerically evaluable.

2. **The tutor is answer-keyed and constrained.** Never free-reasons about the problem. Receives the authored worked solution, hint ladder, the student's wrong answer, and the misconception it matches. Mistake identification works by comparing the learner's wrong answer against the question's named misconception distractors (required by the content schema); a match passes that misconception's name to the tutor prompt so it responds to *this* mistake specifically. An unmatched wrong answer falls back to the next hint rung with no specific diagnosis — expected, not an error.

   **Pause interaction protocol** (per `zen-mode-build-prompt.md` §7): the pause triggers via explicit learner action ("I'm stuck") or is auto-offered after 2 consecutive wrong attempts on the same question. Entering it visibly changes the world state — the grind quiets, the tutor arrives. Every hint ladder has exactly 3 rungs; the tutor asks one question at a time (two sentences maximum), and each learner reply advances at most one rung — there is no open-ended chat. After rung 3, the tutor stops asking and reveals the worked solution step by step. Leaving the pause drops the learner back mid-stream with the question re-presented fresh; a correct answer on resume earns reduced XP with no penalty framing.

   **Latency treatment (eng review issue 8).** The pause's world-quieting transition plays *during* the model request, so the wait reads as the tutor arriving rather than as a frozen screen. Input locks while the request is in flight, preventing double-submits that would burn quota and spend twice for one question. A slow request extends the transition; a timeout resolves it into a visible, honest state rather than an indefinite animation.

   **Leak validation (revised — eng review issue 4, tension 3).** Tutor output is prose, not an expression, so it cannot be handed to the equivalence checker directly. A extraction pass first pulls candidate math fragments from the response (LaTeX spans, digit runs, symbol sequences), normalizes common number-words ("one over x squared") into parseable notation, then parses and numerically compares each fragment against the answer key. An unparseable fragment is treated as suspicious and triggers the fallback. Leaks stated purely in prose with no extractable fragment are handled by *prevention*, not detection: the system prompt explicitly forbids stating the answer in words, and the eval suite (#12) includes fixtures probing for exactly this. A runtime LLM leak-judge was considered and rejected — it would roughly double per-pause cost against a deliberately chosen ceiling.

   A request error or timeout is treated identically to a validation failure. On any of these — validation failure, error, or timeout — retry once at temperature 0 on the same model, then fall back to the raw authored hint. No model escalation, to respect the cost ceiling. Fallback rate is logged with the rest of #7's instrumentation and is a headline quality metric to watch; this slice sets no target threshold — it's observational, not a gate.

3. **Fully usable with the AI layer switched off.** The authored-hint path is the real product; the AI layer is a progressive enhancement over it, not the other way round.

4. **Hard cost ceiling: under US$0.03 per pause** (a single tutor pause interaction, not the surrounding grind session — see #7 for that term). Small/cheap model by default (see #2 — no escalation, only retry-then-fallback). Cache the system prompt and the worked solution. One config module (e.g. `lib/tutor-config.ts`) holds the model id and its full rate card — standard input, cache-write, cache-read, and output rates are distinct and must not be collapsed into a single number up front. Per-pause token budget = cost ceiling ÷ a blended rate computed from a stated assumed token mix, recomputed whenever the config or mix changes. Per-user daily pause quota defaults to 5 (day boundary = local device midnight, per the device clock, since the stack has no server-side clock), in config and logged; when exhausted, the pause UI disables AI tutoring for the rest of that day and falls straight to the authored hint ladder with a visible message. Running estimated cost prints in dev mode.

5. **Progression is mastery-gated, not XP-gated.** Difficulty tiers 1–5 (per `zen-mode-build-prompt.md` §4). 3 correct in a row at a tier promotes; 2 wrong demotes. At tier 1, demotion clamps and resets the streak-to-demote counter; at tier 5, promotion clamps and the learner is tracked as "at cap." Ranks require demonstrated accuracy at a difficulty tier — you cannot grind your way to rank by farming easy questions. The gate must be visible and legible from session 1. Rank count, names, and thresholds remain undefined — see Open Questions. The grind has no timers and no countdown clock; speed is never scored or punished — the pacing fantasy is focused calm, not pressure, which is the entire reason it's called Zen Mode.

6. **Built to be screenshot- and share-worthy from day one.** A visually loud rank-up moment, a summary card composed for a screenshot, and a shareable permalink encoding the summary (score, streak, rank, XP delta) as a compact state blob in the URL, rendered client-side on load. **On decode (eng review issue 6), the blob is Zod-validated; anything malformed or truncated renders a friendly "this summary link is broken" page with a route into the app — never a crash.** There is no server-side data store; the only server component is the tutoring proxy from #9.

7. **Instrument the two risky hypotheses.** Event log for session start/end, per-question latency (excluding time inside a tutor pause — pause duration is logged separately as its own span), correct/incorrect/unparseable, pause invoked/resolved-to-correct, hint rung reached, tutor fallback fired, rank-up, mid-stream abandonment.

   **Storage and export (revised — eng review issue 1).** A browser cannot append to a JSONL file on disk, so events buffer in a dedicated IndexedDB store and a dev-only export produces the `.jsonl` the analytics script reads. No server-side event sink. One script answers: does the pause unstick people (pause → next-attempt-correct rate), and does the loop survive its own novelty (session-1 vs session-5 length, voluntary return). Honest limitation: with a single builder as the only user, both measurements are n=1 and describe *your* practice, not a general population.

8. **Explicit non-scope:** no auth, payments, subscriptions, accounts, multi-device sync, leaderboards, social features, an authoring admin UI, mobile apps, or any B2B/classroom surface. Additionally cut during eng review: coin currency, audio layer, and the linear algebra topic (see NOT in scope).

9. **Stack:** Next.js (App Router) + TypeScript + Tailwind, deployed to Vercel, single package. Dependencies are all Layer 1: `zod` (schema + permalink validation), `idb` (never hand-roll the raw callback-based IndexedDB API), `mathjs` (expression parsing and evaluation), `katex` (LaTeX rendering). IndexedDB persistence behind a typed interface; if IndexedDB is unavailable (some private-browsing modes), the same interface falls back to an in-memory implementation for that session with a visible warning that progress won't save.

   **Deployment posture (revised — eng review issue 2, tension 2).** The app deploys publicly so summary permalinks actually open for the people they're shared with. Protection is applied to `/api/tutor` specifically, not the whole site: an origin check plus a shared secret the app holds, platform rate limiting, and — doing the real work — a hard provider-level spend cap that bounds worst-case loss to a chosen number. A secret shipped in a client bundle is discoverable, so the spend cap is the actual guarantee, not the secret.

   Content lives as YAML under `content/` for the common case (id, difficulty, answer, hint ladder, misconceptions), with MDX only where prose needs richer formatting. Zod-validated at build time — the build fails on invalid content.

10. No third-party sprite packs with unclear licensing (CSS/SVG-drawn assets only). Respect `prefers-reduced-motion` — cut shake and particles, keep state changes.

11. **Unreadable input is its own state (eng review issue 5, tension 4).** Input the parser can't read — empty submits, `x +`, stray brackets, `idk` — is neither correct nor incorrect. It moves no promote/demote counters and breaks no streak, so a typo can never cost a difficulty tier or pollute the accuracy number ranks are gated on. It does not count toward the 2-consecutive-wrong pause trigger either, because notation confusion and conceptual confusion are different problems: after 2 consecutive unparseable submits, show a short notation guide (how to write powers, fractions, roots) instead of invoking the tutor. This costs no pause quota and no API spend. Unparseable submissions are logged as their own event type, so the rate tells you directly whether the parser or the input affordances need work.

12. **The tutor prompt has an eval suite (eng review issue 7).** ~15-20 fixtures of (question, wrong answer, matched misconception) run against four checks: no answer leak in any form including prose, at most one hint rung advanced per turn, at most two sentences containing exactly one question, and the reply actually addresses the named misconception. Without this, every prompt change is a guess and fallback rate — the headline quality metric — can only be tuned by feel.

## Premises

1. The defensible surface is the authored content bank — questions, worked solutions, hint ladders, misconception distractors — not the tutoring conversation itself, since general-purpose AI already commoditizes free-form Socratic tutoring. **Confirmed** — landscape search corroborates: Khanmigo, ChatGPT Study Mode, Gemini for Education, and Socratic by Google have saturated Socratic-style hint tutoring as a commodity; nothing found combines an authored, misconception-keyed question bank + hint-ladder tutor + game presentation into one loop.
2. This is primarily solving the builder's own problem (practicing/relearning calculus) rather than targeting a broad unknown audience. **Confirmed.**
3. Off-the-shelf libraries are used rather than hand-rolled, per the reuse ladder. **Confirmed** — see #9 for the resolved dependency list.
4. Distribution is "deploy to Vercel, share a URL" — no app-store, package-registry, or CLI distribution problem. **Confirmed.**

## Approaches Considered

### Approach A: Minimal viable — follow the build order as written (CHOSEN)
Stage-by-stage per the build order: content schema + validator + questions → authored-hint-only loop playable end to end → presentation pass → progression/persistence → tutor layer → summary card → remaining content → analytics. Effort S/M, Risk Low. Fastest path to something playable; validates "is the loop actually fun" before any AI engineering. Accepted tradeoff: the tutor's answer-leak safety net isn't stress-tested until stage 5 — a known risk window, not a solved problem, until then.

### Approach B: Tutor-safety-first — build and stress-test the validator before the game loop
Write the equivalence checker and tutor output validator as a standalone tested module against synthetic scenarios before any UI exists. Rejected — delays the playable milestone and risks building validation machinery before the loop is proven fun. The underlying concern still shapes how carefully stage 5 gets built.

### Approach C: Feel-first throwaway sketch
A disposable vanilla page nailing pixel rendering, hit feedback, and keyboard flow before committing architecture. Rejected — its only value (de-risking feel) is already covered by stage 3 of the real build order, and throwaway prototypes tend to become permanent scaffolding.

## Recommended Approach

**Approach A**, as scope-reduced by the eng review. It matches the project's own definition of done — "pulling the API key out entirely leaves the app fully playable via authored hints" is a constraint on build *order*, not just a feature checkbox. Building the tutor-safety module against the real loop, once it exists, exercises the validator against real content and real UI rather than a synthetic harness first and a real target second.

## Open Questions

1. **Mid-session interruption/recovery.** Does an in-progress session (mid-grind or mid-pause) survive a tab close or refresh, or is it discarded? IndexedDB makes either possible; this is a product-feel call. Settle before stage 4.
2. **Question exhaustion at a tier.** With ~30 questions across five tiers, a session can exhaust the unused questions at a tier. Decide whether to repeat (risking the mastery gate rewarding memorization) or fall back to an adjacent tier. Settle at stage 2.
3. **Rank names, count, and thresholds.** The gate mechanic is fully specified; the ranks are not. Neither this doc nor the build prompt defines how many exist, what they're called, or which tier/accuracy combination unlocks each ("Ronin" is the only named example). A content decision, not an engineering one. Settle before stage 4.

## Success Criteria

- Complete a 20-30 question session without touching the mouse, and it feels good.
- Get stuck, pause, get genuinely helped without being handed the answer, resume.
- `pnpm validate:content` passes; every answer key is test-verified.
- A correct answer written in an unexpected but equivalent form is accepted, including antiderivatives differing by a constant.
- Pulling the API key out entirely leaves the app fully playable via authored hints.
- Estimated tutoring cost per pause prints in dev and sits under US$0.03.
- The tutor eval suite passes all four checks across its fixtures.
- The summary card is something you'd actually screenshot — and renders correct/total, session streak, XP delta, and rank badge without layout overflow at 1080×1080.
- README explains how to add a question; the analytics script answers pause→correct rate and session-1 vs session-5 length.

## Distribution Plan

Next.js app deployed publicly to Vercel and shared as a URL, with `/api/tutor` protected by origin check + shared secret + platform rate limiting, backstopped by a hard provider spend cap. No app-store, package-registry, or CLI distribution channel.

## Failure Modes

For each new codepath: one realistic production failure, whether a test covers it, whether error handling exists, and whether the user sees it.

| Codepath | Realistic failure | Test | Error handling | User sees |
|---|---|---|---|---|
| `checkAnswer` on antiderivative | Correct answer marked wrong (+C) | Required (stage 1) | Differentiate-before-compare | Would be silent and wrong — **fixed by design** |
| `checkAnswer` sampling | Sample point in undefined domain | Required (stage 1) | Reject + resample, then unparseable | "Can't read that", no penalty |
| `extractMathFragments` | Leak in pure prose, no fragment | Eval fixtures | Prompt prohibition + number-word normalization | Silent if it escapes — **accepted residual risk** |
| `/api/tutor` | Timeout or provider error | Required (stage 5) | Retry at temp 0, then authored hint | Authored hint, pause resolves |
| `/api/tutor` | Abuse burning spend | — | Spend cap + rate limit + origin check | Tutor unavailable, authored hints still work |
| Permalink decode | Truncated/mangled blob | Required (stage 6) | Zod validate | Friendly "link is broken" page |
| Persistence | IndexedDB blocked | Required (stage 4) | In-memory fallback | Visible "progress won't save" warning |
| Analytics export | Store grown very large | — | None yet (see `TODOS.md`) | Slow export |
| Tier selector | Tier runs out of questions | Blocked on Open Question 2 | Undecided | Undecided |

**Critical gaps** (no test AND no error handling AND silent): none remaining. The prose-leak path is silent but has prevention plus eval coverage, so it is an accepted, documented residual risk rather than an unguarded gap.
